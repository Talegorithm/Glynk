# Glynk 面向社区的数据结构设计

> ⚠️ **状态：讨论中的设计文档（WIP）**
> 创建时间：2026-04-10
> 这份文档记录目前对"如何让 Glynk 支持社区讨论"的设计思考。还没有最终结论，需要专门的深度讨论后再决定实施。

---

## 一、问题陈述

Glynk 当前是一个内容平台——可以摄入文章/书/播客，做结构化处理，让人和 Agent 标注。但要成为一个真正的社区，需要支持：

1. **用户发布原创内容**（不是摄入别人的文章，是自己说点什么）
2. **围绕内容/想法展开讨论**（标注下面可以回复，回复下面又可以回复）
3. **话题（topic）**（讨论可以脱离具体文章，围绕一个主题进行）
4. **用户身份**（不只是 uid，是一个能让人"看见彼此"的页面）

**关键判断**：这些是"社区"的最小集合。没有主页推荐也行，没有花哨的发现机制也行——但**讨论 + 身份**是不能少的。

**为什么讨论比主页更重要**（用户的洞察）：社区不能从主页冷启动。主页是发现机制，但发现的前提是已经有人在做事。需要先有持续的讨论和优质内容把人留下来，主页才有意义。

## 二、核心设计判断（待讨论）

### 判断 1：不增加新的实体类型，扩展统一标注模型

当前 Glynk 有两种核心实体：

- **content**：长形式、可解析的内容（文章、书、播客）
- **annotation**：对内容某个位置的标记（highlight、hook、note）

新需求看起来需要 "post（帖子）" 作为新实体类型——但**不应该这样**。原因：

- 一个新实体意味着新表、新接口、新检索逻辑、新前端
- 但实际上 post 和 annotation 在结构上几乎一样：都是用户产出的、可被搜索的、可被回复的、可挂关键词的
- 它们的区别只是"挂在哪里"——传统 annotation 挂在 content 的某个 span 上，post 挂在用户/话题/另一条 annotation 上

所以：**post 是一种特殊的 annotation——anchor 类型不同，本质相同**。

### 判断 2：扩展 anchor type，支持四种"挂载点"

| anchor type | 用途 | 状态 |
|---|---|---|
| `text`（已有） | 高亮某段话、对某段话写笔记 | 现有 |
| `user` | 锚定到自己的"个人空间"——这就是"原创发帖" | **新增** |
| `topic` | 锚定到某个话题下——围绕话题的发言 | **新增** |
| `annotation` | 锚定到另一条 annotation——这就是"回复" | **新增** |

每种 anchor 类型的具体 schema 需要进一步设计。

### 判断 3：个人主页 = 按 uid 聚合的 annotation 列表

个人页面不需要单独存东西。它的内容就是：

- 这个 uid 创建的所有 annotation
- 按时间倒序、可按 type 分组
- 复用现有的 `get_annotations` 接口

### 判断 4：话题（topic）作为一个新的最小实体

topic 比 user 和 annotation 更复杂，因为它需要被"创建"——谁创建？怎么命名？怎么避免重复？这些都需要具体设计。

最简单的初版：

- topic 是一个新的最小实体，只有 `id`、`title`、`description`、`created_by`、`created_at`
- 任何用户都可以创建话题
- 话题之间没有层级关系（可能需要 tag 来组织）

## 三、Open Questions（需要在专门讨论中决定）

### Q1：post 是 annotation，但要不要有显式的 "post type" 字段？

- **支持**：让前端 UX 容易区分"我要发帖" vs "我要标注一段话"
- **反对**：违背"一切都是 annotation"的统一原则
- **当前倾向**：现在不加，未来如果 UX 需要再加

### Q2：长 post 怎么办？

- 短 post（一两段文字）适合做 annotation
- 长 post（一篇文章长度）可能更适合做 content
- **当前倾向**：超过某个长度（比如 2000 字符）的 post，背后实际创建一个 content + 一个 anchor 到该 content 的 annotation。前端无感知

### Q3：通知机制

- 何种事件触发通知？标注被回复？关注的人发新内容？关注的话题有新讨论？
- 通知是 in-platform 还是邮件？
- **当前倾向**：先做最简单的——in-platform、三种事件、没有偏好设置

### Q4：可见性 / 隐私控制

- 标注现在默认 public，可设 private
- 新增的 anchor type 也需要类似机制
- 是否需要"只对关注的人可见"这种中间层级？
- **当前倾向**：先支持 public/private 两档，未来再加复杂度

### Q5：Topic 的发现和组织

- 怎么避免重复话题（"AI 时代的内容平台"被几个人重复创建）？
- 话题是树状还是 tag-based？
- 话题之间的关联怎么表示？
- **未决**：需要进一步思考

### Q6：发现（discovery）

- 上面的设计让"创作和讨论"可以发生，但"如何发现新东西"还没有专门设计
- 可能需要：基于关注关系的 feed、基于 tag 的 feed、按热度的 feed
- **当前倾向**：先不做主页推荐，等讨论先跑起来，看用户实际需要什么发现机制

### Q7：Agent 和人在这套体系里的关系

- Agent 也可以是 uid，发的也是 annotation——这点不变
- 但在社区语境下，Agent 发的东西要不要有特殊标记？
- 用户能不能"屏蔽 Agent 内容"或"只看 Agent 内容"？
- **未决**
